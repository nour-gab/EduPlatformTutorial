### Step 2.2 — Enforce the five-project dependency graph

**Goal**: Resolve the starter's Persistence → Infrastructure mismatch while preserving the inward Dependency Rule, with Persistence and Infrastructure both depending on Application but never on each other.
**Files affected**:
- `starter-solution/src/EduPlatform.Persistence/EduPlatform.Persistence.csproj` (edit)
- `starter-solution/src/EduPlatform.Persistence/Context/ApplicationDbContext.cs` (edit, if needed to remove the direct Identity-type dependency)
- `starter-solution/src/EduPlatform.Infrastructure/Identity/ApplicationUser.cs` (edit, only if the chosen Identity boundary requires it)
**Chapter section**: Ch.02 §2.2
**Planning note**: The current scaffold references `EduPlatform.Infrastructure` from Persistence and imports `ApplicationUser`/`ApplicationRole` there. The chapter requires that reference to be removed, but it does not specify where the shared Identity model should live. Stop and ask the Approver to choose the Identity boundary before editing these files; do not silently move or duplicate the types.
**Verify**:
```bash
dotnet list starter-solution/src/EduPlatform.Persistence/EduPlatform.Persistence.csproj reference
dotnet list starter-solution/src/EduPlatform.Infrastructure/EduPlatform.Infrastructure.csproj reference
dotnet build starter-solution/EduPlatform.sln
```
After the boundary decision, Persistence must list only Application, Infrastructure must list only Application, and the solution must build successfully.
**Understand before continuing**: Why is a project reference to Infrastructure from Persistence an architectural violation even if the code still compiles?
